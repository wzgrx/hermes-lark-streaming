# 0.18.0 紧凑详情：设计契约与验证

2026-10-03。用户最新要求：**好看、紧凑、信息密度高，减少展开后的纵向占用**。此要求替代早先图 2 的三列/五分组长表；图 1 的两行摘要、默认折叠和图 3 的运行态目标继续保留。

## 原生组件设计

- `collapsible_panel` 默认折叠，左侧展开入口；仅详情内部间距改为 4px。
- 顶部两行：服务商/接口/思考；请求与返回模型。仅当原始模型 ID 完全相同且未触及 160 字符安全限长时合为一行；不同、缺失或触及限长时分别展示，不拿相同截断前缀证明身份相同。
- 中间四行 `column_set` 双列：耗时/首响应、输入/输出、缓存读取/命中率、请求尝试及错误/工具数。灰色标签、加粗数值，无五个大分组标题和重复分隔线。
- 底部：末次上下文与占比、统计/费用/压缩说明。发生多个服务商路径才添加对应行。
- 常规示例约八行详情；长字段会换行，差异/切换会增加行数。不为了固定高度隐藏真实差异；标识符仍沿用既有脱敏及 160 字符长度边界。
- 不引入 Node sidecar、浏览器渲染运行时、图片型正文或新的网络请求；保持原有投递 owner、流式和文字复制。

## 思考字段缺失：已复现的机制

使用本地真实 Hermes `ApiRequestHooksMixin._api_request_payload_for_hook` 和合成的 80 条长消息，复现了 `_sanitize_hook_payload` 将整个请求变成 `_truncated`/`preview` 的情况；位于请求体中的 `reasoning_effort=max` 不再是结构化字段。

0.18.0 在观测到该标志且缺少思考参数时显示“请求字段已裁剪”，不解析 preview，不存储对话，不从全局配置冒充本轮实际请求。此复现证明该机制存在，具体生产轮次仍需对应 hook 标志确认。

彻底稳定展示仍需在原始请求裁剪前取得白名单标量，并保留精确请求身份；不能仅放宽整段请求内容大小上限或推测 max。该项仍在计划中，未将原因说明误写成采集已完全修复。
